### Projekt-Kategorien (2026-06-06)
Einteilung der Projekte mit Farben — ein **Manifest-Feld `category`** ist die zentrale Quelle der Wahrheit, schlägt überall durch. Aktuell **10 Kategorien**: 🎨 Hobby · 💼 Arbeit · 🏠 Hausverwaltung · 🗄️ Büro · 👨‍👩‍👧 Familie · 🩺 Gesundheit · 💡 Ideen · 🖥️ Technik · 📚 Lernen · 💰 Finanzen.
- **Definition zentral:** `dashboard/constants.py` → `CATEGORIES` (key → label, color-Hex, emoji). **Erweitern = je ein Eintrag in `CATEGORIES` + `generate_dashboard.py` `CAT_EMOJI`.** (Wekan-Farbfelder entfernt — Wekan am 06.07.2026 ausgemustert.) Endpunkt `GET /categories`. Priority Widget-Knöpfe ziehen die Liste dynamisch (kein Rebuild nötig).
- **Setzen:** `PATCH /boards/<id> {"category":"hobby"}` → setzt `category` UND automatisch `color` = Kategorie-Hex (sofern kein color mitgegeben). Leerer String entfernt.
- **Dashboard-Kachel:** Rahmenfarbe = `color` (folgt Kategorie), `generate_dashboard.py` zeigt Kategorie-Emoji vor dem Namen (`CAT_EMOJI`).
- **Priority Widget:** `kanban_client.get_projects()` lädt jetzt `category`/`color`; `get_categories()`/`set_category()` + Endpunkte `GET /api/projects/categories`, `POST /api/projects/{id}/category`. Frontend: **Schnellknöpfe pro Projekt** (5 Emoji-Buttons → 1 Klick weist Kategorie zu + färbt + gruppiert), Eingang nach Kategorie gruppiert. Nach Backend-Änderung **Priority Widget rebuild** (`podman build` + restart).
- **Auto-Vorkategorisierung:** `dashboard/auto_categorize.py` (einmalig/erneuerbar) — ordnet alle Top-Level-Projekte einer der **13 Kategorien** zu (nur Namen+Tags), PATCH pro Board. `--force` überschreibt bestehende. **KI-Engine seit 2026-06-22: Claude-Abo zuerst** (`_ask_claude` via CLI-Bridge 8950, gratis, Modell `ai_config['categorize_model']`=Haiku), **Ollama nur noch Fallback** (`_ask_ai` = Claude→Ollama→`_HEURISTIC`). Grund: lokales `mistral` hielt das JSON-Format nicht ein (erfand Kategorien) → fiel immer auf Heuristik. Claude trifft die feineren Kategorien (heimnetzwerk/dashboard-meta/ki-projekte) zuverlässig.
- **Auto-Kategorie bei der ERSTELLUNG (2026-06-21):** Neue Projekte/Ideen bekommen sofort eine Kategorie + Farbe — `auto_categorize.categorize_one(name, tags, desc, use_ai)` (Heuristik-first/gratis `_heuristic_or_none`; bei Fehlschlag + `use_ai` → **Claude-Abo**, sonst Ollama; Fallback `ideen`). `board_service.create_board` setzt sie wenn keine mitgegeben (`use_ai=not fast` → fast bleibt instant), der **async Foto-Pfad** `photo_service.analyse_in_background` nach der Vision-Analyse (`use_ai=True`). **Bewusst KEINE Priorität** (`eisenhower` bleibt leer) → neue Projekte erscheinen im 🎯-Modus als 📥 „noch nicht einsortiert" = sofort als neu erkennbar; User korrigiert Kategorie jederzeit per Schnellknopf. E2E verifiziert (Grafana→technik, eisenhower=None).
- **Gotcha (2026-06-06):** `do_PATCH`/`do_DELETE` müssen die Board-ID **url-decodieren** (`urllib.parse.unquote`) — sonst 404 bei Umlaut-IDs (z.B. `logs-prüfen`). urllib-Clients (auto_categorize, project_describer) müssen die ID umgekehrt `quote()`en.

### Projekte archivieren & löschen (Übersicht, NUR Desktop, 2026-06-22)
Pro Projektkachel (`renderCard` in `html/js/index.js`) gibt es oben rechts zwei Aktions-Knöpfe (`.card-actions`/`.card-act`, `stopPropagation` → öffnen das Projekt NICHT): **🗄 Archivieren** (bzw. **♻️ Entarchivieren**) und **🗑 Löschen**. Mobile (`/m/`) bleibt bewusst simpel (nur Lesen+Terminal) — keine Knöpfe.
- **Archivieren** = Manifest-Feld **`archived`** (bool), in PATCH-Whitelist (`board_service.patch_board`) + `_PROJECT_FIELDS` (`dashboard_service`, kommt via `/api/dashboard`). Optimistisch + PATCH-Rollback. Reversibel, nichts geht verloren. Toolbar-Toggle **„🗄 Archiv"** (`#archive-toggle`, JS-State `showArchived`, KEIN localStorage) schaltet die Übersicht auf **nur archivierte** (zum Aufräumen/Entarchivieren); Standard blendet Archiviertes aus (`applyFilter`).
- **Löschen** = `window.API.deleteBoard(id, purge)` → `DELETE /boards/<id>[?purge=1]`. 2 Bestätigungen: (1) überhaupt löschen, (2) **nur bei Ideen** (`p.type==='idea'` / `foto[-_]`-id) auch der Ordner. `delete_board(board_id, purge=False)` entfernt Board-JSON + Manifest; `purge=True` löscht zusätzlich `~/Projekte/<id>`.
- **Sicherheits-Guard `_purge_project_folder` (WICHTIG):** löscht NUR Ordner direkt unter `~/Projekte/`, **niemals `~/containers/`** (echte Container-Quellen) und **niemals Git-Repos** (`.git` vorhanden → abgelehnt). Frontend bietet purge ohnehin nur für Ideen an (Doppelschutz). Getestet: purge eines Idee-Boards löscht den Ordner, Repo-Ordner bleibt unangetastet.
- Deploy: Backend (`board_service`/`dashboard_service`/`api/boards`) → `systemctl --user restart dashboard-api.service`; Frontend (`index.js`/`index.css`/`index.html`, api.js) = nginx-Mount, live, Cache-Bust `?v=20260622-archive`. E2E (Playwright/Chromium) grün: Archivieren→ausgeblendet→Archiv-Ansicht mit ♻️→entarchiviert, keine Console-Errors.

### KI/Ich-Trennung + zentrales Board „Meine Aufgaben" (2026-06-23)
Trennt Aufgaben nach Besitzer, damit der User seine (meist physischen) To-Dos projektübergreifend an EINEM Ort sieht — getrennt von dem, was die KI erledigt. Entscheidungen laufen unverändert über das bestehende Entscheidungs-/Automat-Board (werden bewusst NICHT gespiegelt).
- **Datenmodell:** neues Karten-Feld **`owner`** ∈ `me` (👤) | `ki` (🤖) | leer. `Card`-Schema hat `extra="allow"` → kein Schema-Change nötig.
- **Setzen:** `POST /card-owner {board_id, card_id, owner}` (`app/api/kanban.py` → `board_service.set_card_owner`, atomar via Repo-Lock). Die Route ruft danach **best-effort `mine_collector.collect()`** → Spiegelung ohne Wartezeit. nginx-Regex (`card-owner`) im 8798-Block ergänzt.
- **Frontend (`html/js/project.js`):** pro Aufgaben-Karte zwei Toggle-Knöpfe **👤/🤖** (`renderCard` → `.card-owner-btns`, Funktion `setCardOwner`, optimistisch+Rollback, ruft `API.post('/card-owner')`) + Besitzer-Chip in der Meta-Zeile. NICHT bei KI-Vorschlags-Karten (`isKiCard`) und nicht bei `claudemd-description`. CSS `.owner-btn`/`.owner-active` in `project.css`. Cache-Bust `?v=20260623-owner`.
- **Zentrales Board `meine-aufgaben`** (`📋 Meine Aufgaben`, Kategorie büro): Spalten 📥 Zu erledigen / 🔧 Dran / ⏳ Wartet / ✅ Erledigt + Infokarte. Einmal-Setup: `venv/bin/python setup_meine_aufgaben.py` (idempotent).
- **Sammel-Job `mine_collector.py`** (`collect()`): geht alle **Manifest**-Boards durch (verwaiste Nicht-Manifest-Boards werden übersprungen!), sammelt OFFENE `owner=='me'`-Karten (nicht in Done-Spalte/rejected/Entscheidung) und legt je eine Spiegel-Karte **`mirror::<board>::<cardid>`** in `meine-aufgaben/todo` an. **Idempotent:** existierende Spiegel werden in Titel/Desc aktualisiert, ihre Spalte (User-Fortschritt) bleibt. Manuelle Karten (ohne `mirror::`-id) bleiben unangetastet. Timer **`mine-collector.timer`** (stündlich, +5min Boot) als Sicherheitsnetz. **WICHTIG:** Unit-Dateien **ohne `User=`** (user-Services dürfen kein setgroups → sonst `216/GROUP`-Loop).
- **Drei Zustände statt „offen/weg" (`_mine_state()`, 2026-08-01):** `open` = spiegeln · `finished` = Quelle in Erledigt-Spalte ODER beantwortete Entscheidung (Titel `✅ …`/`🗑️ …`) → **der bestehende Spiegel wandert in die Spalte „✅ Erledigt"** statt gelöscht zu werden bzw. im Eingang liegen zu bleiben · `out` = Quelle weg / nicht mehr `owner=='me'` / rejected / `deleted_at` → Spiegel entfernen. Damit landet eine beantwortete Entscheidung **automatisch** in Erledigt (spätestens beim nächsten Timer-Lauf).
- **Zwei Fallen, die 2026-08-01 zusammen 20 Karten im Eingang festhielten:** (1) `DONE_RE` kannte **„Behoben"** nicht — die Erledigt-Spalte von `home-stack-bugs` heisst so, darum galten die Quellen ewig als offen (Wortliste jetzt identisch mit `DONE_HINTS` in `app/api/automat.py`). (2) Entscheidungen wurden nur am **Label** erkannt, die Bug-Pipeline setzt aber keins → `_is_decision()` prüft jetzt Label **oder** id-Präfix `decision…` **oder** Titel-Marker `ENTSCHEIDUNG:` (gleiche Heuristik wie `automat_lib.is_decision_card`).
- **Ganze Board-Familie statt nur Hauptboard (`_family_boards()`, 2026-08-01):** Der Collector verwaltet `meine-aufgaben` **plus alle Unterboards** (Manifest-`parent_ids`, Fallback id-Präfix `meine-aufgaben-`). Vorher räumte er nur das Hauptboard auf: verschob der KI-Sortierer einen Spiegel in ein Unterboard, sah der Collector ihn nicht mehr, legte im Hauptboard einen zweiten an (**17 Duplikate** live gefunden) und pflegte den im Unterboard nie wieder.
  - **Vorab-Scan über die Familie** (Unterboards ZUERST, Hauptboard zuletzt): jeder `mirror::`-id wird EIN Board zugeordnet. Bei einem Duplikat **gewinnt die Kopie im Unterboard** (dort hat der Sortierer sie thematisch einsortiert) — die Kopie im Hauptboard fliegt raus. So entschieden (01.08.2026), weil das Ping-Pong mit dem Sonntags-Sortierer sonst nie aufhört; die Gesamtsicht liefert die Rollup-Ansicht `GET /board-rollup?id=meine-aufgaben`.
  - Dieselbe id **zweimal im selben Board** wird beim Mutieren zusammengelegt (nur die erste Karte bleibt).
  - Bestehende Spiegel werden gepflegt, **wo sie liegen** (auch im Unterboard); **neu angelegt** wird nur im Hauptboard (`todo`). Die Familie ist nie Quelle (`skip_as_source`), sonst würde sich das Sammelboard selbst spiegeln.
  - Ein Lock **pro Board** (`repo.update` je Familien-Board, nacheinander — nicht verschachtelt). Idempotent verifiziert: zweiter Lauf = 0 Änderungen.
- Deploy: Backend → `systemctl --user restart dashboard-api.service`; nginx-Regex → `podman restart dashboard`; Frontend = nginx-Mount (live, nur Hardreload). E2E Backend verifiziert: owner=me → Spiegel erscheint; owner='' → Spiegel entfernt.

### Eisenhower-Priorisierung pro Thema (Übersicht, 2026-06-16)
In der Projekt-Übersicht (`index.html`) gibt es den Toolbar-Toggle **„🎯 Priorisieren"** (`#eisenhower-toggle`, State `localStorage.idx_eisenhower`). Aktiv → die Übersicht gruppiert **immer nach Kategorie** („Thema") und zeigt **pro Kategorie ein eigenes Eisenhower-Board** mit 5 Zonen: 🔴 `q1` Dringend&wichtig · 🟡 `q2` Dringend oder wichtig · 🟢 `q3` Unwichtig&nicht dringend · ⚫ `q4` Nicht umsetzen (zum Vergessen) · 📥 `""` noch nicht einsortiert. So lassen sich z.B. Hobbys und Technikprojekte **getrennt** priorisieren.
- **Datenmodell = zentrales Manifest-Feld `eisenhower`** pro Board (Werte `q1`..`q4` oder `""`), exakt analog zu `category` → **eine Quelle der Wahrheit**, darum synchron für Übersicht / Priority Widget / Wekan. Liegt in `_PROJECT_FIELDS` (`app/services/dashboard_service.py`, kommt via `GET /api/dashboard`) **und** in der PATCH-Whitelist (`app/services/board_service.py` `patch_board`).
- **Setzen:** Drag&Drop einer Karte in eine Zone **oder** Schnell-Knöpfe pro Karte (🔴🟡🟢⚫📥, auch Touch) → `PATCH /boards/<id> {"eisenhower":"q2"}`. Frontend optimistisch + Rollback bei Fehler.
- **Frontend:** `html/js/index.js` (`eisOn`, `EIS_ZONES`/`EIS_QUICK`, `setEisenhower`, `renderEisCard`, `renderEisenhower`; `applyFilter` verzweigt), CSS `.eis-*` in `html/css/index.css`, Toggle-Button in `index.html`. Reines nginx-Mount (live) → kein Container-Restart, nur Hardreload (Cache-Bust `?v=20260616-eis`). Die **Python-Änderungen** brauchten `systemctl --user restart dashboard-api.service` (erledigt).
- **KI-Prio-Knopf „🤖 KI-Prio" (`#ki-prio-btn`, 2026-06-17):** stuft **noch nicht einsortierte** Projekte (leeres `eisenhower`) per Ollama in q1..q4 ein. **Vom User gesetzte Quadranten bleiben unangetastet** (gehen gar nicht erst an die KI; Frontend überspringt beim Anwenden alles, was schon belegt ist). Frontend sammelt die leeren Projekte (`id,name,category,desc≤160`), `POST /eisenhower-suggest {items,ai}`, dann pro Vorschlag `patchBoard(id,{eisenhower})` (optimistisch) + schaltet in den Priorisieren-Modus + `applyFilter()`. Backend `prio_suggester.suggest_eisenhower(items, use_ai)` → EIN gebündelter Ollama-Call (`_ollama_text`, JSON `[{nr,q}]`, `_parse_nr_map`, max `MAX_AI_PROJECTS=60`), **schreibt nichts** (reiner Vorschlag). Endpoint in `app/api/kanban.py` (`EisenhowerIn`/`EisItem`), nginx-Regex `eisenhower-suggest` ergänzt. Live verifiziert (Finanzen/Speicher→q1, Hobby→q4, Familie→q3). Folgt der Regel „KI nie über User-Eingaben" (vgl. KI-Prio in `project.html`).
- **Priority Widget liest `eisenhower` (2026-06-17, erledigt):** `kanban_client.get_projects` lädt das Feld; Priority Widget zeigt es im Eingang als Vorschlag (Badge + gestrichelter Quadranten-Knopf) + Knopf „🎯 Dashboard-Prio" zum Bulk-Einsortieren (Positions-Mapping q1→Q1…q4→Q4, read-only, schreibt nur in die Priority Widget-Wochen-JSON). Details: `~/containers/priority_widget/CLAUDE.md`.

### Auto-Weiterentwicklungs-Schalter in der Priorisierung (2026-07-20)

- **4 Status:** ⚪ **aus** (`auto=false`) · 🤖 **an** (`auto=true`, offene Karten) · ✅ **alle Kanban erledigt** (`auto=true` + `counts.backlog+in_progress=0`, abgeleitet) · 🙋 **Entscheidung nötig** (`auto=true` + offene Entscheidungskarte, orange/pulsierend). Nur **aus↔an** sind per Klick umschaltbar; 3+4 sind rein **abgeleitet** und schreiben nichts (`autoStateKey(p)`).
- **Datenquellen:** `auto` ist neu in `_PROJECT_FIELDS` (`app/services/dashboard_service.py`) → kommt via `GET /api/dashboard`; „Entscheidung nötig" aus `GET /api/automat/decisions` (in `init()` board-weise in `autoDecisions{}` gesammelt, fehlertolerant).
