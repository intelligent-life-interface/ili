### Kompakte Karten + Detail-Modal (`project.html`, 2026-06-16)
Die Kartenfläche im Board ist **bewusst kompakt** (kurze Spalten): nur Label-Farbbalken, Titel und eine **Meta-Zeile** (`.card-meta`/`.cmeta`) mit ⚡Priorität · ⏱Aufwand + rechtsbündigen **Indikatoren** für verstecktes Material (📝 Beschreibung, 📷 Foto, 🔌 Schnittstellen, 🔗N Refs). Drei Korrekturen (Meldung „Navigation zu übergeordneten Projekten funktioniert nicht"):

Zugehörige Datenbereinigung: 9 `foto-*`-Boards hingen am gelöschten Board `ideen-2` und waren dadurch nirgends auffindbar (nicht Top-Level, kein existierender Parent) — `parent_ids` via `PATCH /boards/<id>` geleert (Top-Level 134 → 143). `paperless` hatte 4 tote `child_order`-Einträge, ebenfalls entfernt. ### Datei-Anhänge (Board + Karte → OneDrive, 2026-06-16)
Anhänge auf **Projekt-Ebene** (Button „📎 Anhänge" in der Board-Tools-Leiste → `#att-modal`) **und Karten-Ebene** (Abschnitt „📎 Anhänge" + „＋ Datei" im Detail-Modal). Beliebige Dateitypen, **max 100 MB**.
- **Speicher:** lokale Arbeitskopie auf der grossen Platte `/mnt/daten/Dashboard-Anhaenge/<board>/<scope>/<att_id>__<name>` (NICHT auf `/`, Mount-Guard wie rclone-onedrive), + Sync per `rclone copyto` in den eigenen OneDrive-Ordner **`FHEM:Dashboard-Anhaenge/...`** (Remote `FHEM:`, type=onedrive). `scope` = `_projekt` oder `card_<id>`.
- **Backend:** `app/services/attachment_service.py` (Logik) + `app/api/attachments.py` (Router, prefix `/api/attachments`): `POST` (multipart `file`,`board_id`,`card_id?`) → speichert lokal + BackgroundTask `sync_to_onedrive` (rclone); `GET /{id}/status`, `GET /file/{id}` (FileResponse aus lokaler Kopie), `DELETE /{id}` (Board-Eintrag + lokal + OneDrive). Status: `uploading`→`synced`/`failed` (bei fail liegt die Datei lokal weiter vor & ist abrufbar). Konstanten in `constants.py` (`ATTACH_*`); `python-multipart` ist im venv.
- **Anhang-Metadaten** leben im **Board-JSON**, immer via `BoardRepository.update` (Lock): Projekt → `board["attachments"][]`, Karte → `card["attachments"][]` (Karte per **stabiler `card.id`** — `project.js` vergibt vor dem Karten-Upload eine id via `genId()`/`saveBoard()`, da neue Karten sonst keine id haben). `update()` erhöht `rev` → das Frontend lädt nach jeder Anhang-Operation das Board still nach (`loadBoard(true)`), sonst F4-Stale-409 beim nächsten autoSave.
- **Frontend:** `project.html` (Button, `#att-modal`, hidden `#att-file-input`, Anhang-Sektion im Bearbeiten-Modal `#edit-att-list`), `project.js` (`openAttModal`/`pickFiles`/`handleAttFiles`/`addCardFiles`/`addEditCardFiles`/`renderEditAttList`/`deleteAtt`/`renderAttList`/`startAttPoll`/`refreshAttViews`), CSS `.att-*` in `project.css`. Indikator `📎N` in der Karten-Meta-Zeile. Reines Frontend (nginx-Mount, live) → kein Restart, nur Hardreload.
- **Zugänge (3 Stellen):** (a) Projekt-Button in der Board-Tools-Leiste, (b) Karten-**Detail**-Modal, (c) Karten-**Bearbeiten**-Modal (`addEditCardFiles`, neue ungespeicherte Karte → Hinweis statt Upload). Dazu auf der **Dashboard-Kachelübersicht** (`index.js`): grünes Badge `📎N` (Quelle: `dashboard_service._count_attachments` → Feld `att_count` in `/api/dashboard`); Klick aufs Badge öffnet `project.html?id=<id>&att=1`, was `project.js` beim Laden erkennt und das Anhänge-Modal öffnet.
- **nginx:** eigener `location ^~ /api/attachments` (schlägt die grosse Regex) mit `client_max_body_size 100m` + 600s-Timeouts. Nach Python-Änderungen `systemctl --user restart dashboard-api.service`; nach nginx-Änderung `podman restart dashboard` (inode-Falle).

#### Automatische Link-Erkennung im Chat (2026-07-11)
Links, die im Projekt-Chat mit der KI geteilt/erwähnt werden (User- **und** KI-Antwort), landen automatisch — ohne manuellen Upload — als Einträge im selben Board-Anhänge (`#att-modal`), **neueste zuoberst**. Nur Board-Ebene (keine Karten-Links).
- **Backend:** `app/services/link_service.py` — `extract_urls(text)` (Regex `https?://…`, dedupliziert, Satzzeichen am Ende abgeschnitten) + `add_from_chat(board_id, role, text)` (dedupliziert gegen bereits vorhandene `type="link"`-Einträge, fügt neue **vorne** in `board["attachments"]` ein: `data.setdefault("attachments", [])[:0] = new_entries`). Eintrag-Felder: `{id, type:"link", url, filename (Kurzlabel), uploaded, source:"chat", role}` — bewusst ohne `size`/`stored_name`/`onedrive_path`, da kein Datei-Gegenstück.
- **Hook:** `chat_service.chat()` (`app/services/chat_service.py`) ruft nach dem `_log_chat_history`-Call `link_service.add_from_chat()` je einmal für `last_user_msg` und `assistant_text` auf — einziger zentraler Ort, an dem beide Texte + `board_id` pro Chat-Turn vorliegen. Fehler dort werden geloggt, aber schlucken die Chat-Antwort nicht (`try/except` um den Hook).
- **Löschen:** läuft über den bestehenden `DELETE /api/attachments/{id}`-Endpunkt — `attachment_service.delete_attachment()` hat einen frühen Guard für `entry["type"] == "link"` (kein Datei-/OneDrive-Cleanup nötig).
- **Frontend:** `renderAttList()` in `project.js` verzweigt bei `a.type === 'link'` auf einen Link-Row (🔗, `target="_blank"`, Badge „💬 Chat" statt Grösse/Sync-Status) — Rest der Anhänge-Logik (Öffnen/Löschen-Button, Modal, Badge `📎N`) unverändert wiederverwendet.
- Tests: `tests/test_link_service.py`. Browser-verifiziert (Playwright) gegen `dashboard.intranet.yourdomain.example`.

### Dedup-Check beim Anlegen neuer Karten (2026-06-16)
Verhindert doppelte Wunsch-/Aufgabenkarten (und damit teure Doppelbearbeitung durch Claude). **Nur warnen + verknüpfen**, blockiert nie.
- **Backend `dedup_finder.py`** → `check_duplicate(board_id, title, desc, use_ai=True)`: zweistufig & billig. (1) **Jaccard-Vorfilter** (lokal, gratis) über Wort-Mengen gegen alle OFFENEN Karten (erledigte Spalten + `claudemd-description` raus). Kein Treffer → sofort fertig, **kein Ollama**. (2) Nur bei Verdacht **Ollama-Bestätigung** (nur Titel, `_ollama_text`), entscheidet welche Kandidaten echte Dubletten sind. Endpoint `POST /dedup-check {board_id,title,desc?,ai?}` (`app/api/kanban.py`) → `{duplicates:[{id,title,column,score,reason}]}`. Fehler/Ollama-Ausfall → leeres Ergebnis (Anlegen nie blockiert).
- **Gotcha (gelöst):** Ollama liefert das Objekt teils **doppelt-kodiert als String** im JSON-Array (`["{\"id\":…}"]`) → `_ai_confirm` parst String-Items nach (`json.loads`), sonst werden bestätigte Dubletten verworfen (Symptom: identischer Titel, trotzdem 0 Treffer).
- **Frontend `project.js`:** `saveCard()` ist jetzt `async`; bei NEUER Karte (`ki===null`) erst `checkDuplicates()`. Treffer → `showDedupWarning()` (Overlay `#dedup-modal`, CSS `.dedup-*` in `project.css`) mit pro Karte „🔗 verknüpfen" + „Trotzdem neu anlegen" + „Abbrechen". **Verknüpfen** legt die neue Karte NICHT an, sondern hängt einen `ref` an die bestehende Karte (`label:"Auch gewünscht: …"`, `note:<neuer Titel>`) → Wunsch geht nicht verloren. `_dedupSkip`/`_pendingNew` steuern den Flow.
- **nginx:** `dedup-check` in der grossen 8798-Regex ergänzt. Nach Änderungen: `systemctl --user restart dashboard-api.service` (Python) + `podman restart dashboard` (nginx). Frontend Cache-Bust `?v=20260616-dedup`.
